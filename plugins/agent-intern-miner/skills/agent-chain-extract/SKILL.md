# Agent 口述链路提取

> 内部 ID：`agent-chain-extract`

## 作用

把“我做过接接口、调模型、改 prompt、看日志”这类零散描述，逐步还原成可面试的 Agent 业务闭环，并把个人实际负责范围和事实缺口分开。

## 输入

- 实习期间做过的事情清单；
- 业务对象、触发入口和用户目标；
- 任务分解、Tool/RAG、状态、失败处理和评测的口述信息；
- mentor/同事负责的部分和可提供的证据。

## 输出

原始工作清单、核心业务链、个人负责位置、上线前后差异、价值节点和待补问题。每个价值节点还要说明业务失败后果、为什么比普通 API/Prompt 更难、适合承载的业务对象和可验证指标。结论标 `[用户事实]` 或 `[待确认]`，建议标 `[建议改造]`。

## 何时使用

没有可读源码、源码属于公司不能带出，或你只记得工作过程但不会组织时使用。若已有本地仓库，优先使用 Agent 源码链路扫描。

## 怎么用

说：“使用 `agent-chain-extract`，我先列出做过的事情，你一次只问我一个问题。”回答完一个问题后再继续，不要一次编造完整项目。

没有源码时不得把口述结果标成 `[源码证据]` 或“代码已验证”。只输出 `[用户事实]`、`[待确认]` 和 `[建议改造]`；后续拿到项目源码时再交给 `agent-chain-scan` 验证。

把零散工作还原成“业务任务 → Agent 编排 → 工具/知识 → 状态/副作用 → 评测/观测 → 用户交付”的事实链。一次只问一个问题，等用户回答后再追问。先形成链路能力卡，再交给 `agent-project-select` 选择业务承载项目；不要先替用户挑一个看起来热门的仓库。

## 追问顺序

1. 让用户列出所有做过的事，不筛选、不修饰。
2. 追问业务对象和触发入口：谁提交什么任务，入口是 API、worker、graph 还是 Tool。
3. 追问任务如何分解、状态是否持久化、是否能中断后续跑。
4. 追问 Tool/RAG 具体副作用、失败、超时、重试、幂等和人工接管。
5. 追问评测/监控：看了哪些轨迹、成功率、错误率、成本或延迟，数据从哪里来。
6. 逐件确认角色：哪些是用户做的，哪些由 mentor/同事决策或操作。
7. 追问上线验证、回滚、灰度和仍未解决的问题。
8. 追问业务失败后果：如果任务错了、重复执行、越权或引用过期知识，会造成什么损失？哪些指标可以验证改善？

## 输出

输出原始清单、核心业务链、用户负责位置、上线前后差异、2–3 个价值节点和待补充空白。每个结论标 [用户事实] 或 [待确认]；推测的改造放 [建议改造]，不能直接写进已完成成果。每个价值节点包含“为什么是亮点、适合融合的业务背景、最小验证”，完成后交给 agent-project-select 或 agent-package。
