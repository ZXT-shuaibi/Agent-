# GitHub Agent 项目筛选

> 内部 ID：`agent-project-select`

## 作用

先抽象曼弗实习中真实接触的高价值链路，再从 GitHub 候选池中筛出一个业务背景更适合简历、且能自然承载这些链路的 Agent 项目。它不是寻找“和曼弗相同的业务”，也不是把链路迁移到曼弗业务；它寻找的是经历承载项目，并在该项目中重实现或改造链路。

## 输入

- 想对齐的业务方向，例如企业知识、客服/工单、研究报告、问数或 DevOps；
- 期望 Python 框架或可接受的技术栈；
- 曼弗实习中真实接触的链路、问题和设计点（可先脱敏描述）；
- 你希望重点包装的高含金量链路；
- 希望采用的简历业务背景，或允许插件从候选背景中推荐；
- 用户确认的 2–4 个短名单项目，才能进入真实拉取。

## 输出

候选池和淘汰理由、短名单、拉取 manifest、本地源码证据、链路承载映射、已有能力/建议改造/完成后可写/当前不可写四栏，以及个人最小负责模块。

## 何时使用

曼弗实习业务不适合直接写简历，但你想把其中真实的 Agent 工程链路放进一个更有业务含金量的独立项目时使用。只想了解开源项目概况时不必启动本模块。

## 怎么用

先说：“使用 `agent-project-select`，根据我在曼弗实习中接触的长程任务、Tool 审批和评测链路，找 4 个不烂大街、能承载这些能力的 Python 业务项目。”看到短名单后回复“确认 1、2、4”或“全部”，插件才会拉取源码。

## 经历承载项目模式

### 正确关系

```text
曼弗实习事实 → 高价值链路抽象 → 业务承载项目筛选 → 目标项目重实现 → 独立项目包装
```

不要执行“把链路迁移到曼弗业务”或“把外部项目冒充曼弗生产系统”。外部项目是业务叙事载体，曼弗实习是技术问题和设计启发的事实来源；二次改造必须在承载项目中真实完成。

### 筛选顺序

1. 先调用 agent-chain-scan 或 agent-chain-extract，确认曼弗实习中的链路属于长程编排、Tool 可靠性、评测、记忆、RAG、观测或治理中的哪几类。
2. 读取 [经历承载项目参考](../../references/business-carrier-scenarios.md)，根据链路选择合规证据链、合同履约、指标口径治理、研发变更风险、知识变更发布、跨系统异常处置等业务背景；拒绝默认落入 AI 客服或普通知识问答。
3. 搜索 GitHub 时同时记录业务对象、生命周期、现有状态层、Tool/数据边界、评测入口和可插入模块。
4. 短名单不能只写“项目很好”，必须写“曼弗链路 → 目标业务模块 → 链路嵌入点 → 最小重实现 → 业务结果”。
5. 只有用户确认短名单后才拉取源码；拉取后验证承载点和至少 5 个跨层源码证据。

搜索脚本和 README 只用于建立候选池。最终设计亮点必须回读拉取到本地的真实源码正文，确认链路嵌入点和调用关系；用户主文遵循 [证据优先与精简讲解](../../references/evidence-first-explanation.md)，代码证据集中放附录，不用大量类名代替业务说明。

### 承载项目评分

优先按以下权重评分，而不是按业务名称相似度评分：业务承载自然度 30%、链路嵌入点 25%、源码证据密度 20%、业务独特性 15%、可实现范围 10%。star 只是弱信号。具体背景按需读取 [经历承载项目参考](../../references/business-carrier-scenarios.md)。

高饱和背景（通用 AI 客服、普通企业知识问答、会议纪要、AI 写作和单次报告生成）默认降权，除非候选有状态闭环、权限/审计、失败恢复和评测等额外工程链路。

### 结果分层

- **独立项目**：用户在外部项目中完成链路重实现，并有测试、日志或评测证据。
- **建议改造**：源码有承载入口，但用户尚未完成改造，只能给出实现计划。
- **当前不可写**：只有 README、设计想法或曼弗实习启发，没有目标项目代码证据。

先研究公开资料和多样候选池，再展示 3–4 个短名单等待用户确认；确认后才运行 [仓库拉取器](../../scripts/pull_github_repos.py)。最终推荐只能来自本地 cloned manifest，且至少有 5 个可定位源码证据。

## 筛选门禁

- 优先研究研究/报告、客服/工单、问数/数据分析、企业知识和 DevOps 闭环。
- 用 [高价值 Agent 链路](../../references/high-value-agent-chains.md) 按闭环、故障、证据、业务价值和可防守性评分。
- star 只是弱信号，必须覆盖中等热度项目；README probe 不能证明源码能力。
- 薄聊天 UI、单次模型调用、简单 prompt、浏览器插件、纯 SDK/框架、硬件/IoT 项目默认淘汰。
- 拉取失败、源码不可读、manifest 非 cloned 或证据少于 5 个的候选不得进入最终推荐。

## 输出四栏

每个候选必须分别写：

1. **已有能力**：[源码证据] 或 [用户事实] 可证明。
2. **建议改造**：[建议改造]，说明最小可实现模块和验证方式。
3. **完成后可写**：完成改造且补齐证据后才可采用的表达。
4. **当前不可写**：[不可写成已完成]，列出缺口和面试风险。

开源仓库默认作为独立项目/课程项目/改造练习，不能未经用户真实参与证据写成曼弗科技实习成果。外部公司事实记录 URL、日期、来源类型和可信度；未知就写未知。

GitHub 调研时按需读取 [GitHub 研究规则](../../references/github-research.md)、[证据协议](../../references/evidence-protocol.md) 和 [输出结构](../../references/output-schema.md)，不要一次加载与当前阶段无关的 reference。
