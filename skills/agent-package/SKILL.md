# Agent 项目/实习包装

> 内部 ID：`agent-package`

## 作用

把已经验证的 Agent 链路和证据写成诚实、可追问、可防守的项目经历。它负责表达和方案演进，不会把开源项目、建议改造或团队成果冒充成你的实习成果。

## 输入

- 源码扫描报告或口述链路；
- 业务背景、目标指标和指标来源；
- 你亲自实现/修改/验证的模块；
- mentor、同事或开源作者负责的部分；
- 可定位的文件、行号、测试、日志或公开链接。

## 输出

项目名称和业务场景、端到端链路、事实账本、建议改造、完成后可写的 3–6 条 bullet、30 秒版、2 分钟版和面试追问。每条 bullet 绑定证据 ID。

## 何时使用

已经知道链路是什么，但不会把它写成简历或面试表达时使用。若证据仍然不足，先回到源码扫描或口述提取。

## 怎么用

说：“使用 `agent-package`，根据这份报告生成简历 bullet；严格区分我已完成、建议改造和当前不可写，不能把它写成曼弗科技实习。”

生成用户主文前读取 [证据优先与精简讲解](../../references/evidence-first-explanation.md)。简历和项目讲解不堆叠代码、路径和类名；证据 ID 留在主文，完整源码定位集中放证据附录。

把链路和证据变成面试官能追问、用户能防守的表达。先判断材料是用户真实实习、真实个人项目还是开源改造练习，再决定措辞；不改变事实。

## 事实门禁

每句话标注 [用户事实]、[源码证据]、[公开资料]、[建议改造] 或 [不可写成已完成]。开源仓库默认作为独立项目/课程项目/改造练习；没有用户参与证据时，不能写成曼弗科技实习成果。指标无来源时写“待测量/估算”，不写虚构提升。

## 一次一层问答

1. 背景：谁提交什么 Agent 任务，原流程的痛点和后果是什么？
2. 目标：成功标准是任务成功率、人工耗时、引用正确率、Tool 成功率、成本还是延迟？
3. 链路：入口 → 分解/编排 → 状态 → 模型 → Tool/RAG → 副作用 → 评测/观测 → 交付。
4. 方案演进：方案 A 为什么不够，方案 B 解决了什么，最终 C 的代价是什么？
5. 角色：用户实际写了/改了哪些模块，哪些决策由 mentor 或团队完成？
6. 证据：每个功能对应文件、行号、测试、监控或公开链接；不足处进入建议改造。
7. 稳定性：checkpoint、恢复、超时、重试、幂等、权限、审计、回滚和人工接管。

## 输出结构

1. 项目名称与业务场景（避免“AI 聊天系统”）。
2. 端到端链路图和 5 个以上本地证据点。
3. 已有能力 [源码证据]/[用户事实]。
4. 建议改造 [建议改造]，写最小模块、验证方式和预计风险。
5. 完成后可写：只有完成改造并补证据后才采用的 bullet。
6. 当前不可写 [不可写成已完成]：列出缺口。
7. 3–6 条简历 bullet，每条带证据 ID、数据来源和面试钩子。
8. 30 秒版、2 分钟版和可能追问。

推荐表达聚焦闭环，例如“参与搭建可恢复的工单任务编排，补齐 Tool 幂等与轨迹回归”；不要只写“调用模型/接入向量库”。
