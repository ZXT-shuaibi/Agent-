# 经历承载项目与高价值业务背景

## 先定义关系

“经历承载项目”是一个业务背景更适合简历的外部项目。曼弗实习提供真实的技术问题、链路和设计启发；外部项目提供可公开验证的业务载体。不能把外部项目说成曼弗的生产系统，也不能把没有在外部项目中实现的设计点写成已完成。

```text
曼弗实习事实 → 抽象链路能力卡 → 选择业务承载项目
→ 在承载项目中重实现/改造 → 测试/评测验证 → 独立项目表达
```

## 承载项目最低条件

一个项目只有同时具备以下大部分条件，才适合承载实习链路：

1. 有明确业务对象，例如合同、供应商、事件、指标、变更、文档或审计案件，而不是只有聊天消息。
2. 有生命周期，例如提交、处理、复核、审批、驳回、重试、交付、归档或回滚。
3. 有可调用的系统边界，例如数据库、搜索、文件、工单、CI、数据目录或第三方 API。
4. 有可追责的证据和责任边界，例如引用、审计日志、审批记录、版本、权限或人工接管。
5. 有可验证的业务结果，例如处理时延、人工复核量、引用正确率、Tool 成功率、任务恢复率或成本。
6. 有清晰的二次开发入口，能把链路放入状态层、Tool 层、评测层或数据层，而不是只能改 prompt。

## 先做链路能力卡，再选背景

项目选择不是从“哪个 Agent 项目热门”开始，而是从实习事实中提取能力卡。能力卡至少写清：

| 卡片字段 | 示例问题 | 不能省略的原因 |
|---|---|---|
| 链路名称 | 是长程编排、Tool 可靠性还是评测回归？ | 防止把组件名当亮点 |
| 业务后果 | 失败会造成越权、错误发布、逾期还是人工返工？ | 决定业务背景是否自然 |
| 关键机制 | checkpoint、幂等、ACL、grader、trace 还是人工审批？ | 决定需要寻找的源码入口 |
| 副作用 | 是否写库、发消息、执行 SQL、更新索引或触发发布？ | 没有副作用就难形成工程闭环 |
| 证据要求 | 需要哪些文件、行号、测试和日志？ | 防止依赖 README 宣传 |
| 最小改造 | 学生能在目标时间内真正实现什么？ | 控制项目范围和角色真实性 |
| 结果指标 | 恢复率、越权拦截率、引用正确率、MTTR 或成本？ | 没有指标就无法证明收益 |

只有能力卡完成后，才把它映射到候选项目的业务对象、生命周期和源码嵌入点。

## 优先背景与详细融合方式

### 1. 合规证据链与整改闭环

- **业务对象与生命周期**：审计案件/控制项；发现 → 证据收集 → 风险判断 → 责任人整改 → 复核 → 关闭/延期。
- **最适合链路**：长程持久化编排、RAG 引用与版本、资源权限、人工审批、审计轨迹、评测回归。
- **为什么比普通聊天更有含金量**：每个判断都需要证据和责任人，错误会带来合规风险；任务可能跨天等待材料，天然需要 checkpoint、暂停恢复和人工接管。
- **源码嵌入点**：案件模型/状态机、文档 ingestion、证据检索 Tool、ACL filter、审批节点、审计事件、案件评测集。
- **最小重实现**：给一个案件流增加状态持久化、证据引用校验、整改 Tool 的幂等键和审批暂停/恢复；补恢复、越权和引用错误测试。
- **可衡量结果**：引用正确率、过期证据命中率、逾期案件数、人工等待时长、恢复成功率。
- **搜索关键词**：`compliance case management agent`, `audit remediation workflow`, `evidence RAG approval`。

### 2. 合同义务与供应商履约协同

- **业务对象与生命周期**：合同条款/履约事项；签署 → 条款抽取 → 任务生成 → 交付回执 → 异常升级 → 验收/归档。
- **最适合链路**：文档抽取、长期记忆、定时长任务、Tool 幂等、异常补偿、人工复核。
- **为什么自然**：条款有日期、责任人、附件和版本，提醒或状态更新有真实副作用；模型不能凭空编造“已履约”。
- **源码嵌入点**：合同解析 pipeline、条款 schema、任务/提醒 worker、供应商 API、回执表、版本记忆和验收评测。
- **最小重实现**：实现条款到履约任务的结构化映射、回执去重、逾期升级和版本更正；补重复消息及旧版本误用测试。
- **可衡量结果**：条款抽取准确率、准时履约率、重复提醒率、人工跟进量、版本误用率。
- **搜索关键词**：`contract obligation workflow`, `supplier compliance agent`, `vendor management automation`。

### 3. 企业指标口径治理与问数审计

- **业务对象与生命周期**：指标定义/查询请求；提问 → 口径识别 → 权限检查 → SQL 生成/审批 → 执行 → 结果解释 → 审计归档。
- **最适合链路**：SQL Tool 安全、指标目录 RAG、权限、评测、成本/延迟治理、血缘追踪。
- **为什么比“数据问答”更强**：答案必须同时证明指标口径、SQL、数据范围和权限；错误可能导致经营决策失真或敏感数据泄露。
- **源码嵌入点**：指标 catalog、SQL parser/validator、tenant ACL、查询审批、数据库 adapter、结果 grader、query trace。
- **最小重实现**：给现有问数入口增加指标白名单、SQL AST 校验、行列权限、查询成本上限和金标准评测；补越权、全表扫描和错误口径样例。
- **可衡量结果**：SQL 正确率、口径一致率、越权拦截率、平均查询成本、p95 延迟。
- **搜索关键词**：`semantic layer text to sql`, `metric governance agent`, `analytics copilot audit`。

### 4. 研发变更风险门禁与发布复盘

- **业务对象与生命周期**：变更单/发布批次；创建 → 影响分析 → 测试/CI → 风险审批 → 发布 → 监控 → 回滚/复盘。
- **最适合链路**：多 Agent 分工、Tool 调用可靠性、长程状态、人工放行、回滚、轨迹评测。
- **为什么自然**：代码、工单、CI 和发布平台是明确系统边界；错误动作有真实线上后果，能体现权限、幂等和人工确认。
- **源码嵌入点**：变更状态模型、Git/CI Tool、风险规则、审批 API、发布 adapter、rollback handler、复盘数据集。
- **最小重实现**：只读影响分析与高风险写操作分级，增加审批 checkpoint、发布幂等键和失败恢复；补 CI 超时、重复发布和回滚测试。
- **可衡量结果**：高风险变更拦截率、发布失败率、回滚时长、误告警率、审批等待时长。
- **搜索关键词**：`agentic devops change risk`, `release approval workflow`, `incident postmortem agent`。

### 5. 知识变更影响分析与内容发布

- **业务对象与生命周期**：知识文档/政策版本；创建 → 审核 → 发布 → 被引用 → 变更影响分析 → 重建索引 → 回滚/下线。
- **最适合链路**：增量 RAG、文档版本、权限过滤、引用评测、记忆生命周期、人工发布。
- **为什么比普通企业知识问答更强**：关注的是知识变化如何影响已有答案和不同租户，而不是一次检索；必须能追溯旧答案使用了哪个版本。
- **源码嵌入点**：ingestion job、versioned index、ACL retriever、citation builder、impact graph、发布审批、索引回滚。
- **最小重实现**：引入文档版本和有效期，构建变更影响样例，发布前跑引用/权限回归，失败可回滚到旧索引。
- **可衡量结果**：引用正确率、过期内容命中率、权限误召回率、回归通过率、重建索引耗时。
- **搜索关键词**：`knowledge base versioning RAG`, `document impact analysis agent`, `policy publishing workflow`。

### 6. 跨系统异常处置与运营值班

- **业务对象与生命周期**：事件/告警；接收 → 分级 → 诊断 → 执行动作 → 验证恢复 → 升级/回滚 → 复盘。
- **最适合链路**：Tool 超时与退避、幂等、补偿、人工接管、trace、成本/延迟治理。
- **为什么含金量高**：每个 Tool 都可能改变生产状态，失败边界和 MTTR 比“回答正确”更重要；天然需要持续任务和审计。
- **源码嵌入点**：事件 consumer、处置 DAG、监控/日志 Tool、动作策略、补偿队列、告警 trace、演练评测集。
- **最小重实现**：实现事件分级、只读诊断与写操作审批、分类型重试和补偿队列；用故障注入验证重复动作和人工接管。
- **可衡量结果**：MTTR、自动处置成功率、重复操作数、误升级率、Tool p95 延迟。
- **搜索关键词**：`incident response agent`, `AIOps remediation workflow`, `on-call automation graph`。

### 7. 采购寻源与供应商准入

- **业务对象与生命周期**：供应商档案/准入申请；提交材料 → 合规核验 → 评分 → 补件 → 审批 → 入库/冻结。
- **最适合链路**：多 Agent 分工、文档 RAG、规则评测、权限、人工审批和证据留存。
- **为什么自然**：材料来源、评分规则和审批责任清晰，适合讲角色边界和证据而不是泛泛的“推荐供应商”。
- **源码嵌入点**：材料 ingestion、供应商 profile、规则 Tool、风险评分、审批流、审计表、准入评测集。
- **最小重实现**：限定材料核验 Agent 与规则复核 Agent 的职责，增加补件循环、审批和材料版本；补冲突评分和越权材料测试。
- **可衡量结果**：材料一次通过率、人工复核量、误放行率、审批时延、证据覆盖率。
- **搜索关键词**：`supplier onboarding agent`, `procurement compliance workflow`, `vendor risk assessment`。

## 背景选择矩阵

用实习链路能力卡与候选项目逐项打分，业务相似度不是主指标：

| 维度 | 权重 | 5 分标准 | 0 分标准 |
|---|---:|---|---|
| 业务承载自然度 | 30% | 业务对象、生命周期和失败后果天然需要该链路 | 只能把聊天页面硬套成业务 |
| 源码嵌入点 | 25% | 状态、Tool、数据、评测/观测至少有 3 类真实入口 | 只有 prompt 或 UI |
| 源码证据密度 | 20% | 克隆后可定位 ≥5 个跨层证据点 | 只有 README 或截图 |
| 业务独特性 | 15% | 非高饱和场景且能说明责任与结果 | 通用聊天/写作 Demo |
| 最小可实现范围 | 10% | 能由学生独立完成并验证一条闭环 | 需要重写整个系统或依赖不可得服务 |

### 选择理由与淘汰理由必须同时写

每个候选不能只写“推荐”，必须写：

```text
选择理由 = 实习链路 → 业务对象/生命周期 → 源码嵌入点 → 最小重实现 → 指标
淘汰理由 = 缺失的状态/副作用/证据/权限/评测 + 对面试和包装的具体风险
```

高饱和背景（通用 AI 客服、普通企业知识问答、会议纪要、AI 写作和单次报告生成）不是绝对淘汰，但必须额外补齐至少两项“知识版本 + 权限过滤”“任务恢复 + 人工审批”“轨迹评测 + 线上回归”等闭环；否则降权。

## 四栏事实账本

选择业务背景时必须同时写清链路嵌入点（源码嵌入点）、选择理由和淘汰理由，不能只给一个业务名称或总分。

对每个最终候选分别输出：

1. **已有能力**：只写本地源码或用户事实可证明的能力，标 `[源码证据]`/`[用户事实]`。
2. **建议改造**：说明目标模块、最小实现、测试和指标，标 `[建议改造]`。
3. **完成后可写**：只有用户真实完成改造且补齐证据后才采用的表达。
4. **当前不可写**：源码、角色、指标或上线证据缺失时明确列出面试风险，标 `[不可写成已完成]`。

GitHub 仓库默认是独立项目/课程项目/改造练习，不能未经用户真实参与证据写成曼弗科技实习成果。最终推荐只能来自 cloned manifest，且源码正文至少有 5 个证据点。
