# 证据优先与精简讲解

## 硬门禁

扫描器只负责定位候选，不能单独证明一条设计亮点或业务链路成立。形成最终结论前必须回读真实源码正文，确认入口、调用关系、状态/副作用和输出；不得只根据类名、文件名、装饰器、关键词命中或 README 推断能力。

源码型结论至少需要 5 个本地证据点，并覆盖入口、编排/状态、Tool/RAG/副作用、评测/观测中的至少 3 段。证据不足时降级为 `[候选链路]` 或 `[待确认]`，不能写成 `[源码证据]`。

口述模式没有源码时，只能输出 `[用户事实]`、`[待确认]` 和 `[建议改造]`。它可以整理思路，但不能替代源码验证。

## 双层输出

### 主文：给用户读

每条链路只保留：

1. 一句话结论；
2. 业务入口到用户交付的链路图；
3. 2–4 个关键机制及其解决的问题；
4. 失败边界、设计取舍和个人负责范围；
5. 1–3 个证据 ID。

主文不大量堆叠代码，不罗列一串文件和类，不逐层复述实现。类名只在它能证明模块边界或关键取舍时出现。

### 证据附录：给复核和面试准备

完整证据放在附录：

| 证据 ID | 路径与行号 | 符号 | 链路位置 | 证明什么 | 可信度 |
|---|---|---|---|---|---|
| E1 | `path/to/file.py:42` | `run_task` | 入口 | 创建持久化任务 | 0.90 |

每个证据摘录只保留证明结论所需的最小片段，通常 3–8 行；优先用自然语言概括，只有调用关系或边界无法说清时才展示代码块。

## 讲解顺序

```text
业务问题 → 为什么普通 API/单次调用不够 → 端到端链路
→ 关键设计 → 失败如何处理 → 如何验证 → 证据 ID
```

不要按“文件 A、类 B、方法 C”讲项目。代码结构是证据，不是主叙事；主叙事必须说明业务对象、状态变化、外部副作用和用户结果。

## 强制区分

- `[源码证据]`：已读取本地真实源码并确认调用/状态关系。
- `[候选链路]`：扫描器命中但尚未回读完整实现。
- `[用户事实]`：用户明确陈述的真实经历。
- `[建议改造]`：目标项目中尚待实现的设计。
- `[不可写成已完成]`：没有源码或完成证据。
