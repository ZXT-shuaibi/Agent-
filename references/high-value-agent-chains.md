# Agent 高含金量链路与亮点判定

这份参考不是热门技术名词清单，而是用来判断一段 Agent 工程是否值得写进简历、应该放进什么业务项目，以及源码扫描后如何解释“为什么有价值”。一条链路只有同时回答“业务为什么需要、系统如何闭环、失败后怎么办、证据在哪里、本人做了什么”，才算可防守的亮点。查找时必须同时记录源码证据、链路嵌入点和可衡量结果。

## 先理解“亮点”是什么

### 亮点不是组件名

以下说法本身不构成亮点：用了 LangGraph、接了向量库、封装了 Tool、改了 prompt、调用了 GPT、做了多 Agent。它们最多是实现手段。亮点必须落在一个工程问题上：不确定的模型输出如何被约束，长时间任务如何不丢状态，外部副作用如何不重复，知识变化如何可追溯，版本变化如何可回归。

不能只写“调用模型”“接入 RAG”“封装 Tool”或“使用多 Agent”；必须写清楚它约束了什么风险、改变了哪条业务链路，以及如何用源码和指标证明。

### 亮点判定公式

```text
亮点强度 = 业务后果 × 闭环程度 × 故障边界 × 证据密度 × 个人可防守性
```

- **业务后果**：失败会不会造成错误审批、重复扣款、错误发布、合规风险或大量人工返工。
- **闭环程度**：是否从入口经过决策、状态、工具/知识、副作用、评测/观测到用户交付，而不是停在模型回答。
- **故障边界**：是否定义超时、脏数据、重复投递、权限不足、模型拒答、人工接管和回滚。
- **证据密度**：是否能从本地源码、测试、日志或评测报告定位至少 5 个证据点，且覆盖至少 3 个链路段。
- **个人可防守性**：能否说明自己改了什么、为什么这么选、如何验证，哪些由 mentor、同事或开源作者完成。

### 每次扫描都要产出“链路能力卡”

不要直接从关键词跳到简历 bullet。先为每个候选链路填写：

| 字段 | 必须回答的问题 |
|---|---|
| 业务问题 | 谁提交什么任务？不用 Agent 会损失什么？ |
| 输入与终态 | 输入对象、成功终态、失败终态和人工接管点是什么？ |
| 决策与状态 | 模型如何决定下一步？哪些状态必须持久化？ |
| 工具与副作用 | 调用了哪些系统？会不会写库、发消息、改配置或触发发布？ |
| 失败边界 | 哪些错误可重试，哪些必须停止、补偿或审批？ |
| 证据集合 | 入口、状态、Tool/RAG、副作用、评测/观测分别由哪些路径和行号证明？ |
| 为什么是亮点 | 它解决了哪个生产级问题，代价和取舍是什么？ |
| 适合融合的业务背景 | 哪类业务对象天然需要这条链路？为什么自然？ |
| 最小改造/最小重实现 | 在承载项目中实际补哪些模块、测试和指标？ |
| 当前边界 | 哪些只是建议改造或尚无个人证据？ |

## S 级：优先寻找并优先融合

### S1 长程任务与持久化编排

**完整链路**

```text
业务任务提交 → 任务分解/状态图 → checkpoint/store → worker 或 Tool 执行
→ 超时/取消/分类重试 → 恢复/续跑 → 人工审核或最终交付
```

**为什么是亮点**：Agent 的难点不是让模型生成下一步，而是任务可能运行几分钟到几天、跨多个系统、期间进程会重启或人工介入。持久化状态和可恢复执行把一次性 Demo 变成可运营的任务系统；幂等和补偿又决定恢复时会不会重复发通知、重复写库或重复发布。面试官可以沿着状态丢失、重复副作用、取消语义和死信处理持续追问，因此含金量高。

**亮点具体是什么**

1. 用明确的状态 schema 区分 `pending/running/waiting_approval/retrying/succeeded/failed/cancelled`，而不是依赖聊天历史猜状态。
2. checkpoint 在关键节点写入任务 ID、版本、输入摘要、已完成步骤和副作用收据；进程重启后能从最后安全点继续。
3. 重试按错误类型分类，有上限、退避和死信；不可重试错误直接转人工或补偿流程。
4. 对外部写操作使用幂等键、去重记录或 outbox，避免“恢复一次，副作用执行两次”。

**源码证据要找什么**

- API、CLI、队列消费者或 webhook 入口，以及生成任务 ID 的位置；
- `TypedDict`、Pydantic model、dataclass、StateGraph state 或数据库表定义；
- checkpoint/store 的写入和读取、worker/queue 的投递、恢复入口；
- timeout、cancel、retry/backoff、dead-letter、compensation、idempotency key；
- 状态迁移测试、重启恢复测试、重复消息测试或任务轨迹日志。

**适合融合的业务背景**

| 业务背景 | 为什么自然 | 最小可做改造 | 可量化结果 |
|---|---|---|---|
| 合规证据收集与整改闭环 | 案件要跨文档检索、责任人确认和整改复核，天级任务很常见 | 案件状态机、证据收集 Tool、审批暂停/恢复、补偿任务 | 恢复成功率、人工等待时长、逾期案件数 |
| 合同义务与供应商履约 | 条款有截止日期，提醒、回执和复核不是一次回答 | 条款任务表、定时 worker、回执幂等、逾期升级 | 准时履约率、重复提醒率、人工跟进量 |
| 研发变更风险门禁 | 需要串联代码分析、CI、审批和发布，失败后必须回滚或暂停 | 变更状态、检查 Tool、人工放行、失败恢复 | 发布失败率、回滚时长、审批等待时长 |
| 跨系统异常处置 | 事件处置要持续更新，工具失败后要留在可恢复队列 | 事件 DAG、分级重试、补偿/人工接管、死信 | MTTR、Tool 重试成功率、重复操作数 |

**最小重实现与验证**：在目标项目里至少实现一个可暂停的状态流、一个持久化 checkpoint、一个带幂等键的外部写 Tool、一次进程重启恢复测试和一条失败转人工的路径。不要只把 `StateGraph` 接上就宣称完成。

**面试追问**：为什么不能只依赖消息队列？checkpoint 写在 Tool 前还是后？恢复时如何知道副作用已经成功？取消运行中的任务是否允许回滚？重试和补偿的边界是什么？

### S2 工具调用可靠性与安全边界

**完整链路**

```text
模型提出调用 → schema/参数校验 → 身份与策略检查 → 超时/退避/熔断
→ 外部副作用 → 结果校验与收据 → 审计/人工确认
```

**为什么是亮点**：模型输出是不可信的，Tool 却可能读敏感数据、改数据库、发邮件、执行 SQL 或触发发布。把 Tool 当成普通函数包装，只解决“能不能调”；可靠性与安全边界解决“谁能调、能调什么、失败会不会造成损失、如何追责”。这是 Agent 从玩具进入企业系统的核心分水岭。

**亮点具体是什么**

1. Tool schema 限制字段、类型、枚举、范围和资源归属；拒绝模型拼出的隐式参数。
2. 授权与业务策略在 Tool 执行前判断，不能只在 prompt 中提醒模型“不要越权”。
3. 读取类、写入类、不可逆操作分级；高风险操作需要人审、二次确认或 sandbox。
4. timeout、重试、熔断和结果校验与副作用类型匹配；写操作必须有幂等或补偿策略。
5. 每次调用记录调用者、任务 ID、参数摘要、策略结果、响应摘要和审计 ID，敏感值脱敏。

**源码证据要找什么**：Pydantic/JSON Schema、Tool registry、allowlist/denylist、tenant/user 权限、SQL parser、timeout/retry/backoff/circuit breaker、sandbox/approval、audit log、幂等键和 Tool 单测。只看到 `@tool` 装饰器不能证明可靠性。

**适合融合的业务背景**

| 业务背景 | 天然副作用 | 最小可做改造 | 可量化结果 |
|---|---|---|---|
| 指标口径治理与问数审计 | SQL 查询可能越权、扫全表或使用错误口径 | SQL AST 校验、指标目录权限、查询审批、结果与口径绑定 | 越权拦截率、查询失败率、口径命中率 |
| 采购寻源与供应商准入 | 材料核验、评分写入和通知有责任归属 | Tool schema、供应商租户隔离、审批和审计收据 | 材料一次通过率、误通知数、审核耗时 |
| 合规整改 | 证据读取和整改状态更新不可越权 | 资源级权限、写操作审批、审计和补偿 | 越权阻断数、整改闭环率 |
| 变更发布风险门禁 | CI、工单和发布系统都是高风险外部系统 | 只读分析与写操作分级、人工放行、回滚 Tool | 高风险变更拦截率、误发布数 |

**最小重实现与验证**：实现一个有 schema 和权限策略的 Tool、一个超时可控的外部调用、一个幂等写操作、一个高风险人工审批分支，并用至少 5 条成功/失败/越权/重复调用样例做测试。

**面试追问**：权限依据来自哪里？提示词注入如何绕过？重试写操作会不会重复？为何选择退避而非立即重试？审计日志如何和一次任务轨迹关联？

### S3 评测与回归体系（含轨迹）

**完整链路**

```text
任务数据集 → Agent 运行 → trajectory/trace → 规则或模型 grader
→ 任务成功率/事实性/引用/Tool 成功率/成本/延迟 → 失败样本回流
→ prompt、模型、检索或 Tool 版本回归
```

**为什么是亮点**：没有评测，所谓“效果提升”通常只是主观 Demo。评测体系把 Agent 改动变成可比较、可回归、可定位的工程变化；同时把最终答案、工具轨迹、引用和成本放到同一条样本上，能回答“到底哪里变好了、哪里退化了”。这是从模型调参走向质量工程的标志。

**亮点具体是什么**

1. 数据集覆盖正常、边界、对抗、权限和失败恢复，而不是只挑成功样例。
2. 记录完整 trajectory：模型版本、状态转移、Tool 参数/结果、检索文档、token、延迟和错误。
3. 评分拆成任务完成、事实性、引用正确、Tool 成功、格式/安全、成本和延迟，避免一个总分掩盖问题。
4. 设定阈值、基线和回归门禁；失败样本可复现并回流数据集，不把一次人工演示当结论。

**源码证据要找什么**：`evals/`、dataset fixture、grader/metric 函数、trajectory schema、阈值配置、CI job、报告生成器、gold answer/citation checker、失败样本保存和版本比较代码。只有 README 写“支持 evaluation”不算证据。

**适合融合的业务背景**

| 业务背景 | 评测对象 | 最小可做改造 | 可量化结果 |
|---|---|---|---|
| 知识变更影响分析 | 新旧知识版本、权限过滤、引用和过期答案 | 版本化 eval 集、引用检查、权限对照集、回归报告 | 引用正确率、旧知识命中率、回归通过率 |
| 指标口径治理 | SQL、指标定义、权限和结果解释 | 金标准查询、SQL/结果 grader、成本延迟阈值 | SQL 正确率、口径一致率、平均查询成本 |
| 研究证据链 | 来源选择、结论和证据覆盖 | 引用完整性评分、事实核验集、失败样本回流 | 证据覆盖率、事实错误率、人工复核量 |
| 异常处置 | 分类、处置动作、恢复结果和告警 | 事件轨迹集、Tool 成功率 grader、MTTR 报告 | 处置成功率、误升级率、MTTR |

**最小重实现与验证**：准备至少 20 条脱敏样例，保存一次完整轨迹，实现 3 个可解释指标和一个基线对比；修改模型/prompt/检索后自动重跑并输出退化样例。没有数据集和可重复运行，不要写“建立评测体系”。

**面试追问**：gold label 从哪里来？模型 grader 如何校准？如何防止评测集泄漏？为什么总分提升但用户投诉增加？成本和延迟是否进入门禁？

## A 级：有跨层证据时同样很强

### A1 记忆与上下文生命周期

**链路**：会话短期状态 → 摘要/压缩 → 长期记忆候选 → 带来源和时间检索 → 租户隔离 → 更正、衰减和删除。

**为什么是亮点**：记忆不是把所有聊天塞进向量库，而是定义什么值得记、谁能看到、过期后怎么办，以及错误记忆如何被纠正。它适合合同履约、供应商档案、案件处置和长期研究，不适合只展示“多轮聊天”。

**源码证据**：memory schema、写入触发条件、摘要器、检索过滤、时间戳/来源、tenant key、删除或更正 API、记忆污染测试。

**最小改造/指标**：实现来源标记和租户过滤，补一条错误记忆更正测试；测记忆命中率、上下文 token、过期记忆误用率。

### A2 数据与 RAG 质量链路

**链路**：增量 ingestion → 文档版本 → 权限过滤 → 召回/重排 → 引用约束 → 反馈和回滚。

**为什么是亮点**：企业知识的难点是新旧版本、权限和引用责任，不是“能搜到一段文字”。当知识变更会影响结论时，版本、ACL、引用和回滚形成可审计的质量闭环。

**源码证据**：ingestion job、版本号/有效期、ACL filter、retriever/reranker、citation builder、索引回滚、recall/precision 或引用评测。

**最小改造/指标**：增加文档版本与权限过滤，建立 20 条引用评测集；测召回率、引用正确率、越权拦截和过期内容命中率。

### A3 可观测性与成本/延迟治理

**链路**：任务 trace → 节点/Tool span → token/费用/延迟 → 错误分类 → 模型路由/降级 → 预算和告警。

**为什么是亮点**：没有 trace，Agent 的慢、贵、错无法定位；有成本与预算边界，系统才具备运营能力。重点是把一次用户任务的模型、检索、Tool 和重试关联起来，而非单纯打印日志。

**源码证据**：trace/span context、correlation ID、token usage、计费表、latency histogram、fallback/router、budget check、告警规则。

**最小改造/指标**：统一任务 trace，记录节点耗时和 token，设置预算超限降级；测 p95 延迟、单任务成本、降级成功率。

### A4 多 Agent 分工与人机协同

**链路**：任务分解 → 角色 Agent → 共享状态/消息 → 冲突检测 → 人工审批/接管 → 合并或回滚。

**为什么是亮点**：多 Agent 只有在角色边界、共享状态和冲突处理清楚时才是工程设计；否则只是多个 prompt 串联。适合研究证据、采购审批和发布复盘等需要不同责任主体的流程。

**源码证据**：角色 contract、handoff message、shared state、交接条件、冲突/超时、人工节点、合并策略和回滚测试。

**最小改造/指标**：限定两个角色和一个人工接管点，补冲突样例；测分工成功率、人工接管率和错误合并率。

### A5 安全治理与策略执行

**链路**：身份/租户 → 输入与文档注入检测 → Tool 策略 → 脱敏/沙箱 → 审计 → 事后追踪与撤销。

**为什么是亮点**：安全治理把“模型可能不可信”转成系统可执行的策略，不依赖 prompt 自觉。它与 Tool 可靠性相互关联，但重点是敏感数据、越权、提示词注入和不可逆动作的治理。

**源码证据**：policy engine、resource scope、injection detector、redaction、sandbox、approval、audit、revocation 或 denylist 测试。

**最小改造/指标**：加入一条资源级权限和一条注入对抗测试，记录审计 ID；测攻击拦截率、误拦截率和审计覆盖率。

## B 级：只能作为配套能力

基础向量检索、prompt 模板、单次 LLM 调用、简单 Tool wrapper、只展示几个角色但没有状态/失败/评测证据，默认是 B 级。它们可以作为 S/A 级链路的组成部分；只有补上版本、权限、增量、恢复、评测或审计等跨层闭环，才可升级为亮点。

## 评分与晋级

每条候选链路按 0–5 分打分：

| 维度 | 0 分 | 3 分 | 5 分 |
|---|---|---|---|
| 业务后果 | 技术演示 | 场景明确 | 失败会造成可说明的业务损失 |
| 闭环 | 单点调用 | 有输入输出 | 状态、副作用、交付和终态完整 |
| 故障边界 | 无处理 | 通用重试 | 分类、退避、幂等、补偿/人工接管 |
| 证据密度 | README/命名 | 2–4 个证据 | ≥5 个跨 3 段可定位证据 |
| 可验证性 | 主观描述 | 有手工样例 | 数据集/日志/测试/阈值可重复 |
| 个人可防守性 | 只会说“用了” | 能讲局部 | 能讲取舍、边界、改动和验证 |
| 业务承载自然度 | 硬套背景 | 可以解释 | 业务对象和生命周期天然需要 |

总分 28 分以上且证据覆盖达标，才进入重点包装；20–27 分进入建议改造；低于 20 分或缺少源码证据，标 `[候选链路]`/`[待确认]`。

## 链路到业务融合的决策顺序

```text
真实实习事实/源码 → 链路能力卡 → 业务对象与生命周期
→ 外部项目源码嵌入点 → 最小重实现与验证 → 独立项目表达
```

选择业务背景时先问“这条链路在该业务中失败会造成什么后果”，再问“项目是否已有可改的状态、Tool、数据和评测入口”。不能因为项目名字听起来像 Agent 就强行融合；如果没有自然副作用和终态，换候选项目。

所有“已有能力”必须标 `[源码证据]` 或 `[用户事实]`；融合方案标 `[建议改造]`；只有用户完成改造并有测试/日志/评测后才可写“完成后可写”。
